# PromptDeck 기술 선택 근거

> 상태: 팀 논의용 초기 결정안  
> 기준: 과제 요구사항 충족, 구현 난이도, 팀 협업 용이성, 향후 확장성

## 1. 기술 선택 기준

PromptDeck은 과제 기간 안에 완성 가능한 로컬 실행형 웹 애플리케이션을 목표로 한다. 따라서 기술 선택 기준은 다음과 같다.

- REST API, DB, Docker, CI/CD 요구사항을 명확히 충족할 것
- 구현 난이도가 지나치게 높지 않을 것
- 팀원이 역할을 나누기 쉬울 것
- 로컬 실행형 도구라는 제품 방향과 어울릴 것
- 이후 개인 프로젝트로 확장 가능한 구조를 가질 것

## 2. Frontend

### 후보 1: React + Vite

특징:
- 컴포넌트 기반 UI 개발에 적합하다.
- JSON 빌더, 프리셋 관리, 채팅 화면처럼 상태가 많은 화면을 만들기 좋다.
- Vite를 사용하면 개발 서버와 빌드 구성이 가볍다.
- 팀 프로젝트에서 프론트엔드와 백엔드를 분리해 작업하기 쉽다.

장점:
- 동적인 UI 구현에 적합하다.
- 컴포넌트 단위 역할 분담이 쉽다.
- 프론트엔드 결과물이 시각적으로 잘 드러난다.

단점:
- Flask 템플릿 방식보다 초기 설정이 조금 더 필요하다.
- CORS, API base URL 등 프론트엔드/백엔드 분리 설정이 필요하다.

### 후보 2: Flask 템플릿 기반 UI

특징:
- 백엔드 서버 하나로 화면과 API를 함께 제공할 수 있다.
- 초기 구현이 단순하다.

장점:
- 설정이 적다.
- 작은 규모의 화면은 빠르게 만들 수 있다.

단점:
- JSON 빌더, 채팅 UI, 동적 폼 관리가 복잡해질수록 유지보수가 어려워진다.
- 프론트엔드 역할 분담과 결과물 표현이 약해질 수 있다.

### 후보 3: Vue + Vite

특징:
- React와 마찬가지로 동적 UI 구현에 적합하다.
- 템플릿 문법이 직관적이다.

장점:
- 폼 중심 화면을 깔끔하게 만들 수 있다.
- Vite와 함께 사용하기 쉽다.

단점:
- 팀원이 React에 더 익숙하다면 학습 비용이 생긴다.

### 선택: React + Vite

선택 이유:
- PromptDeck은 Provider 설정, 프롬프트 프리셋, 요청 JSON 미리보기, 채팅 실행 화면 등 동적 UI가 많다.
- 프론트엔드와 백엔드를 분리하면 팀원이 역할을 나누기 쉽다.
- 과제 결과물에서 UI 완성도를 보여주기 좋다.
- 이후 데스크톱 앱 또는 더 큰 웹앱으로 확장하기 쉽다.

## 3. Backend

### 후보 1: Flask

특징:
- Python 기반의 가벼운 웹 프레임워크이다.
- REST API를 직접 설계하기 좋다.
- 프로젝트 구조를 필요한 만큼만 구성할 수 있다.

장점:
- 구현 난이도가 낮다.
- 과제 기간 안에 MVP를 만들기 좋다.
- SQLite, SQLAlchemy, Docker와 연결하기 쉽다.
- LLM API 요청 처리 로직을 Python으로 작성하기 편하다.

단점:
- Django처럼 관리자 페이지, 인증, ORM 구조가 기본 제공되지는 않는다.
- 프로젝트 규모가 커지면 구조를 신경 써야 한다.

### 후보 2: Django + Django REST Framework

특징:
- DB 모델, 관리자 페이지, 인증, ORM 등 기능이 풍부하다.
- CRUD 중심 서비스에 강하다.

장점:
- 완성도 높은 서버 구조를 만들기 쉽다.
- 사용자 인증, 관리자 페이지가 필요한 경우 유리하다.

단점:
- 초기 설정과 구조가 Flask보다 무겁다.
- 이번 MVP에서는 로그인과 중앙 서버 기능을 제외하므로 장점 일부가 필요하지 않다.

### 후보 3: FastAPI

특징:
- API 서버 개발에 특화된 Python 프레임워크이다.
- 타입 힌트와 자동 API 문서화가 강점이다.

장점:
- 요청/응답 모델 검증이 좋다.
- OpenAPI 문서가 자동 생성된다.
- JSON 중심 API에 잘 맞는다.

단점:
- 과제 예시에 직접 언급된 Flask/Django보다 낯설 수 있다.
- 팀원이 익숙하지 않다면 학습 비용이 생긴다.

### 후보 4: Node.js + Express

특징:
- JavaScript 기반 백엔드 프레임워크이다.
- React와 같은 언어 생태계를 공유할 수 있다.

장점:
- JSON 처리와 비동기 API 호출이 자연스럽다.
- 프론트엔드와 언어를 통일할 수 있다.

단점:
- LLM 관련 Python 생태계와는 거리가 있다.
- ORM, 검증, 프로젝트 구조를 별도로 선택해야 한다.

### 선택: Flask

선택 이유:
- 과제용 MVP에 필요한 REST API를 빠르게 구현할 수 있다.
- 서버 구조가 가벼워 팀원이 이해하기 쉽다.
- 로그인 없는 로컬 실행형 도구와 잘 맞는다.
- SQLite와 연동해 Database Integration 요구사항을 충족하기 쉽다.
- 이후 필요하면 FastAPI나 Django로 확장/전환할 때도 API 설계를 재사용할 수 있다.

## 4. Database

### 후보 1: SQLite

특징:
- 별도의 DB 서버 없이 파일 기반으로 동작한다.
- 로컬 실행형 프로그램과 잘 어울린다.

장점:
- 설정이 매우 쉽다.
- Docker 환경에서도 볼륨으로 관리하기 쉽다.
- 과제의 DB 연동 요구사항을 충족한다.
- 프리셋, Provider 설정, 요청 기록 저장에 충분하다.

단점:
- 다중 사용자 서버 환경에는 적합하지 않다.
- 대규모 동시성 처리에는 한계가 있다.

### 후보 2: PostgreSQL

특징:
- 서버 기반 관계형 데이터베이스이다.
- 실서비스에 많이 사용된다.

장점:
- 확장성과 안정성이 좋다.
- JSON 데이터 저장에도 강점이 있다.
- Docker Compose에서 DB 컨테이너를 보여주기 좋다.

단점:
- 로컬 설치형 도구에는 다소 무겁다.
- DB 서버 설정이 필요하다.

### 후보 3: MySQL/MariaDB

특징:
- 널리 사용되는 관계형 데이터베이스이다.

장점:
- 익숙한 사람이 많다.
- 웹 서비스 DB로 자주 사용된다.

단점:
- 로컬 단일 사용자 도구에는 SQLite보다 설정 부담이 크다.

### 선택: SQLite

선택 이유:
- PromptDeck은 중앙 서버형 서비스가 아니라 로컬 실행형 도구이다.
- 사용자가 Docker 또는 로컬 환경에서 간단하게 실행할 수 있어야 한다.
- 프리셋, Provider 설정, 요청 기록 저장 규모에는 SQLite가 충분하다.
- 과제 요구사항인 Database Integration을 단순하고 명확하게 충족한다.

## 5. API Key 저장 방식

### 후보 1: 브라우저 localStorage 저장

장점:
- 구현이 가장 쉽다.

단점:
- XSS 등 프론트엔드 보안 이슈에 취약하다.
- API Key 관리 방식으로 설명하기 어렵다.

### 후보 2: SQLite에 평문 저장

장점:
- Provider 설정과 함께 관리하기 쉽다.

단점:
- DB 파일이 노출되면 API Key가 그대로 노출된다.
- 보안상 아쉬움이 크다.

### 후보 3: 로컬 설정 파일 저장

장점:
- 사용자가 말한 로컬 프로그램 구조와 잘 맞는다.
- Git 추적에서 제외하기 쉽다.
- 구현 난이도가 낮다.
- 추후 암호화 저장 또는 OS Keychain으로 확장하기 쉽다.

단점:
- 평문 저장인 경우 파일 접근 권한 관리가 필요하다.
- 완전한 보안 저장소는 아니다.

### 후보 4: OS Keychain 저장

장점:
- 보안 측면에서 가장 적절하다.

단점:
- Windows, macOS, Linux별 구현 차이가 있다.
- 과제용 MVP에는 구현 난이도가 높다.

### 선택: 로컬 설정 파일 저장

선택 이유:
- 중앙 서버에 API Key를 저장하지 않는다는 프로젝트 방향과 잘 맞는다.
- 구현 난이도와 보안 설명 사이의 균형이 좋다.
- `.gitignore`로 실제 키 파일을 제외하고, 예시 파일만 제공할 수 있다.
- 추후 OS Keychain 또는 암호화 저장으로 확장 가능하다.

예상 구조:

```text
config/
  secrets.local.json
  secrets.example.json
```

## 6. 로그인 기능

### 후보 1: 로그인 없음

장점:
- 로컬 실행형 도구라는 방향과 잘 맞는다.
- 구현 범위를 줄일 수 있다.
- API Key와 사용자 데이터를 외부 서버에 보내지 않는다는 장점이 명확하다.

단점:
- 다중 사용자 기능이나 팀 공유 기능은 제공하기 어렵다.

### 후보 2: 이메일/비밀번호 로그인

장점:
- 사용자별 프리셋과 기록을 분리할 수 있다.

단점:
- 인증, 비밀번호 저장, 세션 관리 등 구현 범위가 늘어난다.
- 로컬 단일 사용자 도구에는 필요성이 낮다.

### 후보 3: GitHub OAuth

장점:
- GitHub 협업 과제와 어울린다.

단점:
- OAuth 설정과 보안 관리가 필요하다.
- 로컬 실행형 MVP에는 과하다.

### 선택: MVP에서는 로그인 없음

선택 이유:
- PromptDeck은 중앙 서버형 서비스가 아니라 개인 로컬 실행형 도구이다.
- MVP에서는 Provider 설정, 프리셋, 요청 실행이라는 핵심 기능에 집중한다.
- 로그인은 추후 팀 공유 또는 클라우드 동기화 기능을 도입할 때 검토한다.

## 7. Provider 지원 범위

### 선택: OpenAI, Gemini, Claude, Custom API

선택 이유:
- 대표적인 LLM API Provider를 포함해 프로젝트 주제가 명확해진다.
- Custom API를 포함하면 아직 직접 지원하지 않는 Provider도 사용자가 직접 설정할 수 있다.
- Provider Adapter 구조를 사용하면 향후 Ollama, OpenRouter, LM Studio 등으로 확장할 수 있다.

구현 전략:

- 공통 요청 모델을 먼저 정의한다.
- Provider별 Adapter가 공통 모델을 각 Provider의 JSON 형식으로 변환한다.
- MVP에서는 Custom API와 OpenAI-compatible 요청 실행을 우선 구현한다.
- Gemini, Claude는 Provider 타입과 템플릿 구조를 먼저 마련하고, 실제 연동은 일정에 맞춰 구현한다.

## 8. Docker 구성

### 후보 1: Backend만 Docker

장점:
- 구성이 단순하다.

단점:
- 프론트엔드 실행 방식이 별도로 남는다.

### 후보 2: Frontend + Backend

장점:
- 전체 실행 환경을 컨테이너화할 수 있다.
- 과제의 Containerization 요구사항을 명확히 보여준다.

단점:
- Docker Compose 설정이 필요하다.

### 후보 3: Frontend + Backend + DB Container

장점:
- 일반적인 웹 서비스 구조를 보여주기 좋다.

단점:
- SQLite를 선택할 경우 별도 DB 컨테이너가 필요하지 않다.

### 선택: Frontend + Backend + SQLite Volume

선택 이유:
- 로컬 실행형 도구라는 방향과 맞다.
- 별도 DB 서버 없이 Docker Compose로 실행할 수 있다.
- SQLite 파일과 로컬 설정 파일은 볼륨으로 유지할 수 있다.

## 9. CI/CD

### 후보 1: 기본 CI

내용:
- 백엔드 테스트 실행
- 프론트엔드 빌드 확인
- 기본 lint 또는 format 확인

장점:
- 구현 난이도가 낮다.
- 과제의 DevOps 요구사항을 충족한다.

단점:
- 자동 배포는 포함하지 않는다.

### 후보 2: CI + Docker Build

내용:
- 기본 CI에 Docker image build 검증을 추가한다.

장점:
- Docker 요구사항과 연결된다.
- 배포 준비 상태를 더 잘 보여준다.

단점:
- workflow 시간이 늘어날 수 있다.

### 후보 3: CI + 실제 배포

내용:
- 클라우드 또는 서버로 자동 배포한다.

장점:
- 가장 완성도 높은 DevOps 구성이 된다.

단점:
- 클라우드 계정, 비용, 비밀값 관리가 필요하다.
- 로컬 실행형 MVP에는 우선순위가 낮다.

### 선택: 기본 CI + Docker Build 검증

선택 이유:
- 과제 요구사항을 충분히 만족한다.
- 실제 클라우드 배포 없이도 CI/CD 파이프라인을 보여줄 수 있다.
- PR마다 자동 검증을 수행해 협업 품질을 높일 수 있다.
